# Domain Model v1

**Концептуальная модель предметной области**

Магистерское исследование · системный анализ и управление  
Рабочая версия 1.0

---

# 1. Назначение документа

`Domain Model v1` объединяет результаты, полученные в рамках:

- `Domain Scope & Boundaries v1`;
- `Glossary v1`;
- `Domain Process Structure v1`;
- `Domain Actors & Work Types Map v1`;
- `Research_Passport`;
- `Research Problem Package v1`;
- `Research Methodology Package v1`.

Цель документа — сформировать единую концептуальную модель исследуемой предметной области, которая показывает:

1. основные сущности предметной области;
2. их иерархию;
3. отношения между сущностями;
4. связь процесса с участниками;
5. связь процесса с событиями и состояниями;
6. связь процесса с информационными объектами;
7. потенциальные точки возникновения отклонений;
8. основу для последующего AS-IS анализа.

`Domain Model v1` является **концептуальным baseline**, а не утверждённой фактической моделью предприятия.

---

# 2. Основное модельное представление

Исследуемая предметная область представляется как система взаимосвязанных сущностей:

**Бизнес-процесс**

↓ состоит из

**Подпроцессов**

↓ включает

**Задачи / работы**

↓ реализуемые через

**Операции**

↓ порождающие / изменяющие

**События**

↓ приводящие к

**Изменениям состояний**

↓ которые могут фиксироваться через

**Информационные объекты**

и связаны с

**Участниками и ролями**

Результаты этих взаимодействий могут проявляться как:

**нормальное выполнение / ожидание / отклонение / возврат / повторное действие / завершение.**

---

# 3. Основные классы сущностей

В модели выделяются следующие классы:

| Класс | Назначение |
|---|---|
| **Process** | Представляет исследуемый бизнес-процесс |
| **Subprocess** | Представляет устойчивый фрагмент процесса |
| **Task / Work** | Представляет конкретную единицу деятельности |
| **Operation** | Представляет отдельное действие |
| **Event** | Представляет зафиксированный факт действия или изменения |
| **State** | Представляет состояние процесса или задачи |
| **Transition** | Представляет изменение состояния |
| **Participant** | Представляет участника процесса |
| **Role** | Представляет функциональную роль участника |
| **Information Object** | Представляет данные, документ, запись, статус или иной информационный объект |
| **Resource** | Представляет необходимый для выполнения ресурс |
| **Decision** | Представляет точку принятия решения |
| **Deviation** | Представляет отклонение фактического хода процесса |
| **Result** | Представляет результат выполнения |
| **Information Source** | Представляет источник, из которого можно получить данные |
| **Requirement** | Представляет условие, сформированное в результате анализа GAP |
| **Metric** | Представляет измеримый показатель исследуемой характеристики |

Последние три категории относятся преимущественно к аналитическому уровню модели и будут подробнее использоваться на последующих этапах исследования.

---

# 4. Иерархия процессных сущностей

Базовая структура:

**Process**

→ `contains`

**Subprocess**

→ `contains`

**Task / Work**

→ `implemented by`

**Operation**

При этом:

**Task**

может иметь:

- начало;
- одно или несколько действий;
- исполнителя;
- входные условия;
- выходной результат;
- связанные события;
- состояние;
- информационные объекты.

---

# 5. Процесс

## Определение

**Process** — организованная последовательность взаимосвязанных действий, решений, событий, состояний и информационных взаимодействий, направленных на получение определённого результата.

## Основные атрибуты

Концептуально процесс может характеризоваться:

- идентификатором;
- названием;
- целью;
- входами;
- выходами;
- границами;
- участниками;
- подпроцессами;
- состояниями;
- событиями;
- результатами.

## Связи

Процесс:

**включает** подпроцессы;

**включает** задачи;

**взаимодействует** с участниками;

**использует** информационные объекты;

**порождает** события;

**изменяет** состояния;

**производит** результат.

---

# 6. Подпроцесс

## Определение

**Subprocess** — относительно самостоятельная часть процесса, имеющая собственную цель, набор действий и результат.

Подпроцесс позволяет декомпозировать исследуемый процесс без преждевременного перехода к отдельным операциям.

## Основные связи

**Process → contains → Subprocess**

**Subprocess → contains → Task**

При этом не предполагается, что каждый процесс обязательно должен иметь одинаковое количество уровней декомпозиции.

Фактическая глубина определяется потребностями исследования.

---

# 7. Задача / работа

## Определение

**Task / Work** — конкретная единица планируемой или выполняемой деятельности.

Задача является ключевой связующей сущностью между управленческой частью процесса и фактическим выполнением.

## Задача характеризуется

- содержанием;
- приоритетом;
- планируемым сроком;
- фактическим сроком;
- исполнителем;
- состоянием;
- результатом;
- связанными событиями;
- необходимыми ресурсами;
- информацией.

## Связи

**Task → belongs to → Process / Subprocess**

**Task → assigned to → Participant**

**Task → has → State**

**Task → generates → Event**

**Task → uses → Information Object**

**Task → requires → Resource**

**Task → produces → Result**

---

# 8. Операция

## Определение

**Operation** — отдельное действие исполнителя или информационной системы.

Операция является наиболее детальным уровнем текущей концептуальной модели.

Она будет использоваться при дальнейшем AS-IS анализе только там, где детализация необходима для решения исследовательской задачи.

## Связи

**Task → consists of → Operation**

**Participant → performs → Operation**

**Operation → generates → Event**

**Operation → changes → State**

**Operation → uses → Information Object**

Не каждая техническая операция обязательна для включения в итоговую модель.

---

# 9. Участник

## Определение

**Participant** — человек, организационная единица, функция или информационная система, участвующие в выполнении процесса либо в обмене необходимой информацией.

Участник является субъектом взаимодействия с процессом.

## Связи

Участник:

**выполняет** операции;

**отвечает за** определённые задачи;

**создаёт** информацию;

**использует** информацию;

**принимает** решения;

**фиксирует** события;

**получает** информацию о состоянии процесса.

---

# 10. Роль

## Определение

**Role** — функциональная позиция участника относительно конкретной задачи, действия, решения или информационного взаимодействия.

Один участник может выполнять несколько ролей.

Одна роль может реализовываться несколькими участниками.

Поэтому:

**Participant ≠ Role**

---

# 11. Информационный объект

## Определение

**Information Object** — данные, документ, запись, статус, сообщение или иной информационный объект, который создаётся, изменяется, передаётся или используется в процессе.

## Информационный объект может

- описывать задачу;
- отражать состояние;
- фиксировать событие;
- содержать результат;
- передавать решение;
- отражать план;
- содержать фактическую информацию.

## Связи

**Task → uses → Information Object**

**Operation → creates / updates → Information Object**

**Event → recorded in → Information Object**

**Participant → creates / consumes → Information Object**

**Information Object → belongs to → Information Source**

---

# 12. Источник информации

## Определение

**Information Source** — конкретный источник, из которого могут быть получены данные об исследуемом процессе.

Источником может быть:

- информационная система;
- документ;
- база данных;
- журнал;
- запись;
- файл;
- сообщение;
- иной доступный исследовательский источник.

Источник информации является **элементом информационного контура**, но сам по себе не становится объектом исследования только вследствие наличия данных.

---

# 13. Событие

## Определение

**Event** — зафиксированный факт действия, изменения или наступления условия в процессе.

Событие может быть связано с:

- задачей;
- участником;
- временем;
- операцией;
- информационным объектом;
- состоянием.

## Концептуальная структура события

**Event**

→ относится к `Process / Task / Operation`

→ имеет `Timestamp`

→ может быть инициировано `Participant`

→ может изменить `State`

→ может быть зафиксировано в `Information Object`.

---

# 14. Состояние

## Определение

**State** — характеристика текущего состояния задачи или процесса в определённый момент времени.

Состояние может относиться к:

- задаче;
- подпроцессу;
- процессу;
- ресурсу;
- информационному объекту.

Для исследования наиболее важны состояния задачи и процесса.

---

# 15. Переход

## Определение

**Transition** — изменение состояния в результате события или действия.

Концептуально:

**State A**

→ `Event`

→ **Transition**

→ **State B**

Например:

**Planned**

→ `Work Assigned`

→ **Assigned**

или:

**In Progress**

→ `Control Result: Deviation`

→ **Returned for Correction**

---

# 16. Статус

Статус является информационным представлением состояния в определённом информационном контуре.

Поэтому:

**State ≠ Status**

Состояние описывает фактическое или концептуальное состояние процесса.

Статус является тем, **как это состояние представлено или зарегистрировано**.

В исследовании необходимо отдельно проверять:

**фактическое состояние → зарегистрированный статус.**

Именно здесь потенциально возникает проблема неполной наблюдаемости.

---

# 17. Ресурс

## Определение

**Resource** — материальный, информационный, временной, кадровый или иной ресурс, необходимый для выполнения задачи или операции.

В рамках предметной области потенциально рассматриваются:

- материалы;
- инструменты;
- оборудование;
- документация;
- квалифицированный персонал;
- рабочее время;
- доступность необходимых условий.

Ресурс включается в модель только в той степени, в которой он влияет на исследуемый процесс.

---

# 18. Решение

## Определение

**Decision** — выбор направления дальнейшего выполнения процесса на основании имеющейся информации, условий и правил.

Примеры:

- принять задачу в работу;
- изменить приоритет;
- изменить план;
- переназначить исполнителя;
- вернуть задачу;
- подтвердить завершение.

## Особенность

Решение не обязательно является отдельной формальной записью.

Оно может быть:

- явно зарегистрировано;
- выражено изменением состояния;
- отражено изменением плана;
- зафиксировано косвенно через последовательность событий.

Это будет проверяться эмпирически.

---

# 19. Отклонение

## Определение

**Deviation** — различие между ожидаемым, плановым, нормативным или допустимым состоянием процесса и фактическим выполнением.

Отклонение может относиться к:

- сроку;
- последовательности;
- состоянию;
- исполнителю;
- ресурсу;
- результату;
- информационному состоянию.

## Концептуальная связь

**Baseline / Expected State**

↕

**Actual State**

↓

**Deviation**

Отклонение не считается автоматически проблемой.

Сначала оно должно быть обнаружено и интерпретировано, после чего может быть установлено, имеет ли оно исследовательское значение.

---

# 20. Результат

## Определение

**Result** — состояние, продукт или подтверждённый итог выполнения задачи, операции или процесса.

Результат может быть:

- положительным;
- промежуточным;
- не соответствующим ожиданию;
- требующим дополнительного действия.

Результат связан с закрытием задачи, но:

**результат ≠ факт закрытия.**

Задача может быть формально закрыта при наличии различий между ожидаемым и фактическим результатом, если такое будет установлено evidence.

---

# 22. Центральная модель фактического выполнения

Для исследовательских целей центральной частью Domain Model является следующая цепочка:

**Participant**

↓

выполняет

**Operation**

↓

порождает

**Event**

↓

вызывает

**State Transition**

↓

формирует новое

**State**

↓

которое должно быть отражено в

**Information Object**

Таким образом:

**реальное действие**

→ **событие**

→ **изменение состояния**

→ **информационная фиксация**

являются связанными, но не тождественными элементами.

Именно эта связь является основой будущего исследования наблюдаемости.

---

# 23. Плановое и фактическое представление

Domain Model должна поддерживать два параллельных представления.

## Плановое

**Task**

→ Planned State

→ Planned Event

→ Planned Time

→ Planned Result

## Фактическое

**Task**

→ Actual Event

→ Actual Time

→ Actual State

→ Actual Result

После сопоставления:

**Planned ↔ Actual**

могут быть выявлены:

- временные отклонения;
- отклонения состояния;
- изменения последовательности;
- изменения ресурсов;
- изменения исполнителей;
- возвраты;
- ожидания;
- повторные действия.

---

# 24. Информационная наблюдаемость

В рамках модели возникает принципиальная цепочка:

**Actual Process**

↓

**Actual Event**

↓

**Recorded Event**

↓

**Available Information**

↓

**Observable State**

Если один из переходов нарушается, возникает потенциальная потеря наблюдаемости.

Например:

**действие произошло**

→ событие не зафиксировано

→ состояние трудно восстановить.

Или:

**событие зафиксировано**

→ информация доступна с задержкой

→ состояние формально наблюдаемо, но недостаточно своевременно для управления.

Следовательно:

**Observability** и **Timeliness** являются связанными, но различными характеристиками.

---

# 25. Информационная нагрузка

На уровне Domain Model информационная нагрузка формируется взаимодействием:

**Participant**

↔

**Information Sources**

↔

**Information Objects**

↔

**Decision**

Для участника информационная нагрузка может возрастать, когда необходимо:

- использовать несколько источников;
- переключаться между системами;
- самостоятельно сопоставлять данные;
- искать отсутствующую информацию;
- уточнять состояние у другого участника;
- повторно вводить данные;
- интерпретировать неоднозначные статусы.

Данная модель не утверждает наличие всех перечисленных факторов в конкретной организации; они являются объектами последующей проверки.

---

# 26. Domain Model и процессная иерархия

Концептуальная иерархия:

**Domain**

↓

**Process**

↓

**Subprocess**

↓

**Task**

↓

**Operation**

Параллельно существует динамическое измерение:

**Event**

↓

**Transition**

↓

**State**

И информационное измерение:

**Information Source**

↓

**Information Object**

↓

**Information Representation**

А организационное измерение:

**Participant**

↓

**Role**

↓

**Action / Decision**

Таким образом, Domain Model представляет предметную область не как одну последовательность, а как **четыре взаимосвязанных измерения**:

1. процессное;
2. динамическое;
3. информационное;
4. организационное.

---

# 27. Четыре измерения модели

## 27.1. Процессное измерение

**Process → Subprocess → Task → Operation**

Отвечает на вопрос:

> Что выполняется?

---

## 27.2. Динамическое измерение

**Event → Transition → State**

Отвечает на вопрос:

> Что происходит и как меняется состояние?

---

## 27.3. Организационное измерение

**Participant → Role → Action / Decision**

Отвечает на вопрос:

> Кто выполняет работу и принимает решения?

---

## 27.4. Информационное измерение

**Information Source → Information Object → Event / State representation**

Отвечает на вопрос:

> Какая информация сопровождает процесс и как состояние становится наблюдаемым?

---

# 28. Связь четырёх измерений

Полная концептуальная схема:

**PROCESS**

↓

**TASK**

↓

**OPERATION**

↓

**EVENT**

↓

**STATE**

↓

**INFORMATION OBJECT**

и одновременно:

**PARTICIPANT**

↓

**ROLE**

↓

**OPERATION / DECISION**

и:

**INFORMATION SOURCE**

↓

**INFORMATION OBJECT**

↓

**OBSERVABLE STATE**

Таким образом, один фрагмент процесса может быть представлен одновременно:

- через деятельность;
- через участника;
- через изменение состояния;
- через событие;
- через информационную фиксацию.

Это и создаёт основу для многомерного анализа.

# 29. Пример концептуального фрагмента

Рассмотрим абстрактный фрагмент без привязки к конкретной организации:

**Task: выполнение технической работы**

↓

**Participant: исполнитель**

↓

**Operation: выполнение работы**

↓

**Event: завершение рабочей операции**

↓

**State: результат готов к контролю**

↓

**Information Object: запись о выполнении**

↓

**Participant: контрольная функция**

↓

**Decision: результат подтверждён / выявлено несоответствие**

При подтверждении:

**State → Completed / Ready for Closure**

При несоответствии:

**State → Returned for Correction**

↓

**Operation: корректирующее действие**

↓

**Event: повторное завершение**

Такой фрагмент демонстрирует, почему процесс нельзя описывать только списком этапов.

# 30. Модель отклонения

Концептуально отклонение может возникнуть в нескольких точках:

### Временное

**Planned Time ≠ Actual Time**

### Состояний

**Expected State ≠ Actual State**

### Последовательностное

**Expected Sequence ≠ Actual Sequence**

### Ресурсное

**Planned Resource ≠ Actual Resource**

### Информационное

**Required Information ≠ Available Information**

### Организационное

**Planned Participant / Role ≠ Actual Participant / Role**

Все эти типы отклонений являются кандидатами для дальнейшего исследования, но их реальная распространённость должна быть установлена evidence.

---

# 31. Domain Model и исследовательский GAP

Модель позволяет представить потенциальный GAP как расхождение между:

**необходимой структурой процесса и информационной поддержки**

и

**фактически доступной структурой и информацией.**

Например:

**Task requires State Information**

но:

**Information Source does not provide sufficient state evidence**

что может приводить к:

**Reduced Observability**

Аналогично:

**Event occurs at T1**

но:

**Information becomes available at T2**

где:

**T2 > T1**

может возникать потенциальная проблема своевременности.

# 35. Что модель пока не утверждает

`Domain Model v1` не устанавливает:

- фактическое количество процессов;
- фактическую структуру предприятия;
- конкретные должности;
- реальные статусы системы;
- конкретные базы данных;
- точный набор событий;
- точные переходы состояний;
- фактические KPI;
- наличие конкретных информационных разрывов;
- наличие конкретного GAP;
- эффективность конкретной технологии;
- архитектуру будущей подсистемы.

Все эти характеристики должны быть установлены в дальнейшей исследовательской работе.

# 36. Правила развития Domain Model

Новая сущность добавляется в модель только при наличии:

1. исследовательской функции;
2. связи с существующей сущностью;
3. evidence либо обоснованной необходимости для будущей проверки;
4. отличия от уже существующего понятия.

Новая связь должна быть:

- семантически определённой;
- проверяемой;
- необходимой для одного или нескольких RQ.

Нельзя добавлять сущность только потому, что она существует в архитектуре конкретной ИС.

# 39. Критерий готовности Domain Model v1

Документ считается достаточным baseline, когда:

- основные сущности предметной области определены;
- между сущностями установлены однозначные отношения;
- процессное, динамическое, организационное и информационное измерения связаны между собой;
- процесс можно представить через `Process → Task → Operation`;
- динамику можно представить через `Event → Transition → State`;
- участника можно связать с `Role → Action / Decision`;
- состояние можно связать с `Information Object`;
- плановое и фактическое выполнение разделены;
- отклонение имеет понятное положение в модели;
- `Observability`, `Timeliness` и `Information Load` имеют связь с объектами модели;
- модель не превращается заранее в конкретную архитектуру решения;
- модель может быть использована как основа для `Domain Map`, `Process Hierarchy` и будущего AS-IS.
