# 1. Назначение пакета

Настоящий документ объединяет и синхронизирует два взаимосвязанных артефакта:

- `Glossary v1`;
- `Domain Map v1`.

Их объединение необходимо для проверки того, что:

1. каждое ключевое понятие имеет однозначное определение;
2. понятия используются в карте предметной области в том же значении;
3. разные уровни анализа не смешиваются;
4. связи между сущностями соответствуют их определениям;
5. доменная карта не содержит сущностей, отсутствующих в глоссарии;
6. глоссарий не содержит критических сущностей, которым не найдено место в доменной карте;
7. терминология не противоречит `Research_Passport`;
8. концептуальная модель не превращается заранее в AS-IS или архитектуру будущей системы.

Пакет является **терминологическим и концептуальным baseline** перед дальнейшим исследованием заинтересованных сторон, иерархии процессов и фактического AS-IS.

# 3. Исследовательская граница

Объект исследования:

**Бизнес-процессы технического обслуживания и ремонта авиационной техники на предприятии гражданской авиации.**

Предмет исследования:

**Методы и информационные средства анализа, мониторинга и интеллектуальной поддержки управления бизнес-процессами технического обслуживания и ремонта авиационной техники.**

Доменная карта рассматривает процесс не как отдельную информационную систему и не как набор технических операций, а как взаимодействие:

**процессов → деятельности → участников → событий → состояний → информации → результатов.**

# 4. Терминологическая архитектура

Все ключевые понятия разделяются на четыре уровня.

## Уровень A — процессный

**Process → Subprocess → Task / Work → Operation**

## Уровень B — динамический

**Event → Transition → State**

## Уровень C — организационный

**Participant → Role → Action / Decision**

## Уровень D — информационный

**Information Source → Information Object → Information Representation**

Связь этих уровней:

**Participant**

→ выполняет

**Operation**

→ порождает

**Event**

→ изменяет

**State**

→ отражается через

**Information Object**

→ доступный из

**Information Source**.

# 10. Термины, которые принципиально не являются синонимами

## Процесс ≠ задача

Процесс состоит из связанных действий и этапов.

Задача является единицей деятельности внутри процесса.

## Задача ≠ операция

Задача может включать несколько операций.

## Событие ≠ состояние

Событие отражает факт изменения.

Состояние отражает положение процесса или задачи.

## Состояние ≠ статус

Состояние может существовать фактически.

Статус представляет это состояние в информационном контуре.

## Участник ≠ роль

Участник является носителем деятельности.

Роль определяет его функциональное участие.

## Информационный объект ≠ источник

Информационный объект является содержанием информации.

Источник является местом или механизмом её получения.

## Отклонение ≠ проблема

Отклонение — наблюдаемое расхождение.

Проблема — исследовательски значимое нежелательное состояние или затруднение.

## GAP ≠ проблема

GAP формализует расхождение между требуемым и существующим состоянием.

## KPI ≠ Construct

KPI — измеримый показатель.

Construct — концептуальная исследовательская характеристика.

# 12. Организационный контур

```text
              PARTICIPANT
                    │
                  plays
                    │
                    ▼
                  ROLE
                    │
                    ▼
             ACTION / DECISION
                    │
                    ▼
          OPERATION / TASK
                    │
                    ▼
```

**Participant → Role → Action / Decision → Operation → Event**

# 13. Ресурсный контур

```text
                 RESOURCE
                    │
            required by
                    │
                    ▼
              TASK / WORK
                    │
                    ▼
               OPERATION
```

Ресурсы рассматриваются только в той степени, в которой они влияют на исследуемый процесс.

# 14. Информационный контур

```text
          INFORMATION SOURCE
                    │
                    ▼
          INFORMATION OBJECT
                    │
          ┌─────────┼──────────┐
          ▼         ▼          ▼
        EVENT     STATE       TASK
          │         │
          └────┬────┘
               ▼
```

Информация является связующим элементом между фактическим процессом и возможностью наблюдения его состояния.

# 16. Наблюдаемость

Центральная для H1 цепочка:

```text
ACTUAL PROCESS
      │
      ▼
ACTUAL EVENT
      │
      ▼
RECORDED EVENT
      │
      ▼
AVAILABLE INFORMATION
      │
      ▼
OBSERVABLE STATE
```

Наблюдаемость может ограничиваться при:

- отсутствии записи;
- неполноте записи;
- отсутствии контекста;
- фрагментации источников;
- несогласованности;
- недоступности информации.

Все такие механизмы должны быть проверены evidence.

---

# 17. Своевременность

Для H2 используется временная последовательность:

```text
T1 — actual event
 ↓
T2 — event recording
 ↓
T3 — information availability
 ↓
T4 — decision / action
```

Основные интервалы:

**T2 − T1** — задержка фиксации.

**T3 − T1** — задержка доступности информации.

**T4 − T3** — интервал между доступностью информации и решением.

---

# 18. Информационная нагрузка

Для H3:

```text
PARTICIPANT
     │
     ▼
INFORMATION SOURCES
     │
     ▼
INFORMATION OBJECTS
     │
     ▼
SEARCH / COMPARISON / INTERPRETATION
     │
     ▼
DECISION / ACTION
```

Потенциальные проявления:

- несколько источников;
- переключение между источниками;
- ручное сопоставление;
- поиск информации;
- повторный ввод;
- запрос сведений у других участников;
- неоднозначность статусов.

# 19. Процессный слой Domain Map

Концептуальный поток:

```text
1. NEED
   ↓
2. REGISTRATION
   ↓
3. ANALYSIS
   ↓
4. PLANNING
   ↓
5. PREPARATION / PROVISION
   ↓
6. ASSIGNMENT
   ↓
7. EXECUTION
   ↓
8. CONTROL
   ↓
9. CLOSURE
```

Внутри потока возможны:

```text
WAITING
   ↕
EXECUTION

CONTROL
   ↓
RETURN
   ↓
CORRECTION
   ↓
EXECUTION

EXECUTION
   ↓
REPLANNING
   ↓
EXECUTION
```

# 20. Связь процессного и организационного уровней

| Процессный этап | Основные функциональные категории участников |
|---|---|
| Возникновение потребности | инициирующая, техническая, управленческая |
| Регистрация задачи | планирующая, информационная, инициирующая |
| Анализ | инженерная / техническая |
| Планирование | планирующая, управленческая, техническая |
| Обеспечение | материально-техническая |
| Назначение | планирующая, управленческая |
| Выполнение | производственно-исполнительная |
| Контроль | контрольная, техническая, качество |
| Закрытие | исполнительная, контрольная, информационная |

Это **функциональная карта**, а не фактическая организационная схема.

# 30. Контроль относительно Research Problem Package

Проблемная часть исследования предполагает анализ:

# 32. Правило перехода от Domain Map к эмпирической модели

При получении evidence:

**Conceptual Entity**

↓

проверка

↓

**Observed Entity**

↓

подтверждение / уточнение / удаление

↓

**Empirical Domain Model**

Поэтому Domain Map не должна механически копироваться в AS-IS.

AS-IS должен быть построен исходя из:

**actual events + actual states + actual participants + actual information.**

---

# 33. Правило изменения терминов

Если дальнейшие исследования показывают, что термин требует изменения:

1. сначала изменяется его определение;
2. затем проверяются все документы, где термин используется;
3. проверяется Domain Map;
4. проверяются `Research Questions` и `Research Tasks`;
5. проверяется `Research_Passport`;
6. при существенном изменении обновляются зависимые документы.

Нельзя менять смысл термина только в одном документе.

---

# 34. Критерий готовности интегрированного пакета

`Glossary v1 + Domain Map v1` считается готовым baseline, если:

- все ключевые сущности имеют определения;
- определения однозначны;
- сущности присутствуют и в Glossary, и в Domain Map;
- процессные уровни не смешиваются;
- организационный уровень отделён от процессного;
- динамический уровень отделён от информационного;
- состояние отделено от статуса;
- событие отделено от состояния;
- участник отделён от роли;
- источник информации отделён от информационного объекта;
- плановое и фактическое выполнение разделены;
- отклонение имеет определённое место;
- GAP появляется только после анализа;
- H1, H2 и H3 имеют соответствующие элементы модели;
- карта поддерживает RQ0–RQ13;
- карта поддерживает Research Tasks;
- карта не предполагает заранее конкретное технологическое решение;
- карта не выдаётся за фактический AS-IS.
