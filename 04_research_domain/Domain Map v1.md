# Domain Map v1

**Единая карта предметной области**

Магистерское исследование · системный анализ и управление  
Рабочая версия 1.0

---

# 1. Назначение документа

`Domain Map v1` объединяет результаты предыдущих артефактов 4-й недели:

- `Domain Scope & Boundaries v1`;
- `Glossary v1`;
- `Domain Process Structure v1`;
- `Domain Actors & Work Types Map v1`;
- `Domain Model v1`.

Карта предназначена для формирования единого представления предметной области, в котором одновременно отображаются:

- процессная структура;
- основные типы деятельности;
- участники;
- роли;
- события;
- состояния;
- информационные объекты;
- ресурсы;
- решения;
- результаты;
- отклонения;
- информационный контур.

`Domain Map v1` является промежуточным baseline между концептуальным пониманием предметной области и последующим эмпирическим исследованием фактического процесса.

Документ не заменяет:

- `Process Hierarchy`;
- `Stakeholder Map`;
- `RACI`;
- BPMN;
- SIPOC;
- AS-IS Process Model;
- Event Log / Event & State Model.

Он создаёт структурную основу для их последующего построения.

---

# 2. Основная идея карты

Предметная область рассматривается как взаимодействие четырёх взаимосвязанных измерений:

### Процесс

**Process → Subprocess → Task → Operation**

### Динамика

**Event → Transition → State**

### Организация

**Participant → Role → Action / Decision**

### Информация

**Information Source → Information Object → Process / Event / State**

Эти измерения объединяются через фактическое выполнение:

**Task → Operation → Event → State → Information**

при участии:

**Participant → Role → Action / Decision**

и использовании:

**Resource → Information Source → Information Object**

# 3. Границы предметной области

В карту включаются процессы, связанные с:

- возникновением и регистрацией потребности в технической работе;
- анализом и уточнением задачи;
- планированием;
- обеспечением выполнения;
- назначением исполнителей;
- подготовкой;
- фактическим выполнением;
- контролем;
- закрытием и фиксацией результата;
- возвратами;
- ожиданиями;
- повторными действиями;
- изменениями плана.

В информационную границу включаются сведения, необходимые для анализа:

- задач;
- событий;
- состояний;
- сроков;
- исполнителей;
- ресурсов;
- результатов;
- отклонений;
- информационных взаимодействий.

Внешние процессы и системы учитываются через их интерфейсы с исследуемым процессом.

# 6. Типы деятельности

Каждому процессному этапу соответствуют потенциальные типы работ.

| Процессный этап | Типы работ |
|---|---|
| Возникновение потребности | выявление, инициирование, регистрация |
| Регистрация | создание записи, классификация |
| Анализ | уточнение, интерпретация, технический анализ |
| Планирование | определение сроков, последовательности, ресурсов |
| Обеспечение | поиск, резервирование, подготовка ресурсов |
| Назначение | распределение задач, определение исполнителя |
| Подготовка | подготовка рабочего места, документации и ресурсов |
| Выполнение | техническая работа, операции, фиксация результатов |
| Контроль | проверка, инспекция, подтверждение |
| Коррекция | устранение несоответствия, повторное выполнение |
| Закрытие | фиксация результата, завершение задачи |

# 7. Организационный слой

Основные функциональные категории:

1. управленческая функция;
2. планирующая функция;
3. инженерная / техническая функция;
4. производственно-исполнительная функция;
5. контрольная / инспекционная функция;
6. материально-техническое обеспечение;
7. информационная / системная функция;
8. функция качества и соответствия;
9. внешний участник.

Эти категории не являются утверждённой организационной структурой.

Они определяют **функциональные роли**, которые должны быть проверены при дальнейшем изучении фактического процесса.

# 9. Динамический слой

Динамика процесса определяется событиями и состояниями.

Базовая логика:

**State A**

↓

**Event**

↓

**Transition**

↓

**State B**

Например:

**Planned**

→ событие `исполнитель назначен`

→ **Assigned**

или:

**In Progress**

→ событие `выявлено несоответствие`

→ **Returned for Correction**.

---

# 10. Рабочая карта состояний

Для концептуального уровня используется следующая последовательность:

**Not Initiated**

↓

**Registered**

↓

**Under Analysis**

↓

**Planned**

↓

**Ready for Execution**

↓

**Assigned**

↓

**In Progress**

↓

**Under Control**

↓

**Completed**

Эти состояния являются рабочими концептуальными категориями.

Они не должны автоматически интерпретироваться как фактический набор статусов используемой информационной системы.

---

# 11. Нелинейная динамика

Основная линейная цепочка дополняется обратными потоками.

### Возврат

**Control → Correction → Execution**

### Ожидание

**Preparation / Execution → Waiting → Execution**

### Перепланирование

**Execution → Replanning → Execution**

### Переназначение

**Assignment → Reassignment → Execution**

### Повторное выполнение

**Control → Rework → Control**

Таким образом, карта допускает:

**циклы, возвраты, ожидания и повторения.**

Это важно для дальнейшего анализа фактического процесса.

---

# 12. Информационный слой

Информационный слой располагается поверх процесса и обеспечивает его наблюдаемость.

Основная структура:

**Information Source**

↓

**Information Object**

↓

**Event / State / Task**

В качестве информационных объектов могут рассматриваться:

- записи задач;
- статусы;
- документы;
- временные метки;
- сведения об исполнителях;
- сведения о ресурсах;
- результаты;
- решения;
- комментарии;
- сведения об отклонениях;
- сообщения между участниками.

---

# 13. Источники информации

Концептуально могут существовать следующие классы источников:

- корпоративные информационные системы;
- журналы;
- базы данных;
- документы;
- файлы;
- сообщения;
- записи операций;
- экспертные сведения;
- результаты наблюдений.

Для каждого источника впоследствии необходимо установить:

- что именно он фиксирует;
- когда информация появляется;
- насколько она полна;
- насколько она достоверна;
- кому доступна;
- как связана с другими источниками.

# 14. Информационные интерфейсы

Карта предполагает несколько типов информационного взаимодействия.

### Между планированием и исполнением

**план → назначение → фактический статус → результат**

### Между исполнением и контролем

**результат → проверка → подтверждение / отклонение**

### Между обеспечением и исполнением

**потребность → готовность ресурса → предоставление**

### Между участниками и информационными системами

**ввод → хранение → изменение → получение → интерпретация**

### Между управлением и процессом

**состояние → информация → решение → изменение**

# 15. Ресурсный слой

Ресурсы рассматриваются как условия, необходимые для выполнения задач.

Основные группы:

- персонал;
- материалы;
- инструменты;
- оборудование;
- время;
- документация;
- информационные ресурсы.

Связь:

**Task → requires → Resource**

При отсутствии ресурса возможна цепочка:

**Task → Waiting → Resource Available → Execution**

Данный механизм является потенциальным источником временных отклонений.

---

# 16. Решения

Решение связывает информацию с изменением процесса.

Обобщённая структура:

**Information**

↓

**Assessment**

↓

**Decision**

↓

**Action**

↓

**State Change**

Примеры решений:

- принять задачу;
- изменить приоритет;
- изменить план;
- назначить исполнителя;
- переназначить исполнителя;
- начать или приостановить работу;
- вернуть задачу;
- подтвердить результат;
- закрыть задачу.

---

# 17. Результаты процесса

Процесс должен производить результаты на нескольких уровнях.

### Результат задачи

Конкретный результат выполнения технической работы.

### Результат подпроцесса

Завершение соответствующего этапа.

### Результат процесса

Подтверждённое завершение рассматриваемой цепочки деятельности.

### Информационный результат

Зафиксированное состояние, событие, результат или решение.

Поэтому:

**результат деятельности**

и

**информационная фиксация результата**

рассматриваются как различные сущности.

---

# 18. Отклонения

Отклонение появляется при сравнении:

**Expected / Planned**

и

**Actual**.

Основные классы:

### Временное

**Planned Time ≠ Actual Time**

### Состояний

**Expected State ≠ Actual State**

### Последовательности

**Expected Sequence ≠ Actual Sequence**

### Ресурсов

**Planned Resource ≠ Actual Resource**

### Организации

**Planned Participant ≠ Actual Participant**

### Информации

**Required Information ≠ Available Information**

Не каждое отклонение является проблемой.

Его исследовательское значение должно быть установлено отдельно.

# 20. Наблюдаемость в Domain Map

Наблюдаемость определяется цепочкой:

**Actual Process**

↓

**Actual Event**

↓

**Recorded Event**

↓

**Available Information**

↓

**Observable State**

Возможны различные разрывы.

### Потеря события

Событие произошло, но не было зафиксировано.

### Потеря контекста

Событие зафиксировано, но не содержит необходимой информации для интерпретации.

### Фрагментация

События находятся в разных источниках.

### Несогласованность

Источники содержат противоречивые сведения.

### Недоступность

Информация существует, но не доступна необходимому участнику.

Эти механизмы должны исследоваться далее, а не считаться доказанными заранее.

---

# 21. Своевременность в Domain Map

Для анализа своевременности выделяются четыре временные точки:

**T1 — момент фактического события**

↓

**T2 — момент фиксации**

↓

**T3 — момент доступности информации**

↓

**T4 — момент управленческого решения**

Основные временные интервалы:

**T2 − T1**

— задержка фиксации;

**T3 − T1**

— задержка доступности информации;

**T4 − T3**

— интервал между доступностью информации и решением.

Эта структура станет основой дальнейшей операционализации H2.

---

# 22. Информационная нагрузка в Domain Map

Для участника:

**Participant**

↔

**Information Sources**

↔

**Information Objects**

↔

**Decision / Action**

Информационная нагрузка потенциально возрастает при:

- росте количества используемых источников;
- необходимости переключения;
- ручном сопоставлении информации;
- необходимости поиска данных;
- повторном вводе;
- неоднозначности статусов;
- необходимости запроса информации у других участников.

Данные признаки должны быть проверены эмпирически.

# 23. Связь процессов, участников и информации

Обобщённая модель:

```text
                       PROCESS
                          │
              ┌───────────┼───────────┐
              │           │           │
              ▼           ▼           ▼
            TASK      PARTICIPANT   RESOURCE
              │           │
              │           ▼
              │          ROLE
              │           │
              ▼           ▼
         OPERATION ←── ACTION
              │
              ▼
            EVENT
              │
              ▼
            STATE
              │
              ▼
     INFORMATION OBJECT
              │
              ▼
     INFORMATION SOURCE
```

Таким образом, каждый существенный элемент процесса может быть рассмотрен через:

**что произошло → кто участвовал → какое состояние изменилось → какая информация это отражает.**

- реальные операции;
- реальные события;
- реальные состояния;
- реальные статусы;
- реальные информационные источники;
- фактические временные характеристики;
- фактические причины отклонений;
- фактический GAP.

Именно эти элементы должны быть постепенно заменены или уточнены evidence.

---

# 29. Правила использования Domain Map

### Правило 1

Нельзя воспринимать концептуальную связь как доказанную фактическую связь.

### Правило 2

Нельзя добавлять новую сущность без исследовательской функции или evidence.

### Правило 3

Нельзя превращать информационную систему в объект исследования только потому, что она участвует в информационном потоке.

### Правило 4

Нельзя заменять фактические процессы концептуальной схемой при построении AS-IS.

### Правило 5

Нельзя вводить конкретную технологию как обязательный элемент Domain Map.

### Правило 6

Существенное изменение границ или структуры должно быть трассировано обратно в `Research_Passport`.

# 30. Ограничения модели

`Domain Map v1` не является:

- организационной схемой;
- картой конкретной информационной системы;
- BPMN-моделью;
- AS-IS моделью;
- SIPOC;
- RACI;
- event log;
- архитектурой будущей подсистемы.

Она является **интегрирующей концептуальной картой предметной области**.

# 32. Критерий готовности Domain Map v1

`Domain Map v1` считается достаточным baseline, когда:

- объединены результаты предыдущих доменных артефактов;
- процессный, организационный, динамический и информационный уровни связаны;
- основные сущности имеют определённое положение в общей модели;
- видна связь между участником, действием, событием, состоянием и информацией;
- показана связь между плановым и фактическим выполнением;
- определено место отклонения;
- определено место потенциального GAP;
- карта поддерживает RQ1–RQ13;
- карта поддерживает задачи исследования;
- карта не выдаёт концептуальную структуру за фактический AS-IS;
- карта пригодна для перехода к следующей фазе исследования.

# 34. Роль Domain Map в дальнейшей работе

После завершения `Domain Map v1` сформирована единая концептуальная основа:

**Где исследуем?**  
→ `Domain Scope & Boundaries`

**Какими понятиями описываем?**  
→ `Glossary`

**Какие процессы рассматриваем?**  
→ `Domain Process Structure`

**Кто участвует и какие работы выполняются?**  
→ `Domain Actors & Work Types Map`

**Как все сущности связаны?**  
→ `Domain Model`

**Как вся предметная область выглядит целиком?**  
→ `Domain Map`

Следующий этап должен переводить эту концептуальную карту в **более конкретную организационно-процессную структуру**, не перескакивая сразу к AS-IS: сначала необходимо определить заинтересованные стороны и их связь с процессом.
