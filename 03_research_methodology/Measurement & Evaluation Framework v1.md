# Measurement & Evaluation Framework v1

## 1. Назначение документа

`Measurement & Evaluation Framework v1` определяет систему измерения и оценки результатов исследования и переводит гипотезы H1–H3 в операциональные конструкты, переменные, метрики, правила расчёта и критерии сравнения.

Документ обеспечивает связь:

**Research Problem**

→ **Research Questions**

→ **Hypotheses**

→ **Constructs**

→ **Variables**

→ **Metrics**

→ **Measurement Procedure**

→ **Baseline / Proposed Approach**

→ **Evaluation**

→ **Hypothesis Assessment**.

Основная задача framework — исключить ситуацию, при которой гипотеза оценивается субъективно или на основании показателя, который не соответствует её смыслу.

---

# 2. Общая логика измерения

В исследовании используются три центральных конструкта:

1. **Наблюдаемость процесса**
2. **Своевременность обнаружения**
3. **Информационная нагрузка пользователя**

Они соответствуют гипотезам:

**H1 → Наблюдаемость**

**H2 → Своевременность**

**H3 → Информационная нагрузка**

Каждый конструкт измеряется независимо.

Нельзя использовать один показатель как доказательство нескольких гипотез без дополнительного обоснования.

---

# 3. Принципы оценки

## 3.1. Operationalization

Каждый теоретический конструкт должен иметь наблюдаемые переменные.

Например:

**наблюдаемость**

не измеряется напрямую как абстрактное качество.

Она операционализируется через:

- количество релевантных событий, доступных для анализа;
- долю фактических отклонений, которые можно выявить;
- полноту восстановления процесса;
- наличие необходимых состояний и переходов.

---

## 3.2. Baseline comparison

Основным способом оценки предлагаемого подхода является сравнение:

**Baseline**

против

**Proposed Approach**.

Это позволяет оценивать не абсолютное качество решения, а изменение относительно исходного состояния.

---

## 3.3. Принцип одинаковых условий

При возможности baseline и proposed approach должны использовать:

- одинаковые сценарии;
- одинаковые исходные данные;
- одинаковые определения событий;
- одинаковые правила оценки;
- одинаковые критерии результата.

Меняется преимущественно способ обработки и представления информации.

---

## 3.4. Multi-metric evaluation

Ни одна из H1–H3 не должна оцениваться только одним показателем.

Для каждого конструкта используется основной показатель и несколько дополнительных показателей.

Это снижает риск сделать вывод из одного случайного результата.

---

# 5. H1 — Наблюдаемость

## 5.1. Формулировка H1

**Представление фактического выполнения процесса в виде событий, состояний и переходов позволит выявлять отклонения и информационные разрывы, которые недостаточно видимы при использовании разрозненных источников информации и ручного контроля.**

---

# 6. Конструкт H1

## Наблюдаемость

Под наблюдаемостью в рамках исследования понимается способность исследуемого подхода представить фактическое состояние и прохождение процесса таким образом, чтобы релевантные события, состояния и отклонения могли быть обнаружены и интерпретированы.

Наблюдаемость не означает абсолютную полноту информации.

Она определяется относительно:

- исследуемого процесса;
- выбранного набора событий;
- определённых критериев релевантности.

---

# 7. Основная метрика H1

## Detection Completeness

Определяется как:

**Detection Completeness = Number of Relevant Deviations Correctly Detected / Total Number of Relevant Deviations**

или:

\[
DC =
\frac{N_{detected}}{N_{actual}}
\]

где:

- `N_detected` — количество действительно существующих релевантных отклонений, обнаруженных подходом;
- `N_actual` — общее количество релевантных отклонений, установленных по reference evidence.

Значение находится в диапазоне:

**0 ≤ DC ≤ 1**

или:

**0–100%.**

---

# 8. Reference Set для H1

Для расчёта `N_actual` должен существовать reference set фактически возникших отклонений.

Он формируется на основе:

- наблюдения;
- проверенных event records;
- документов;
- экспертной верификации;
- иных допустимых источников.

Reference set не должен формироваться исключительно из результатов proposed approach.

Иначе возникнет circular reasoning.

---

# 9. Дополнительные метрики H1

## 9.1. Event Coverage

\[
EC =
\frac{N_{observable\ relevant\ events}}
{N_{required\ relevant\ events}}
\]

Показывает, какая часть требуемых событий реально наблюдаема.

---

## 9.2. State Coverage

\[
SC =
\frac{N_{observable\ required\ states}}
{N_{required\ states}}
\]

Показывает, насколько полно можно определить необходимые состояния процесса.

---

## 9.3. Deviation Coverage

\[
DevC =
\frac{N_{detected\ deviation\ classes}}
{N_{relevant\ deviation\ classes}}
\]

Используется, когда важно оценивать не количество отдельных случаев, а разнообразие типов отклонений.

---

# 10. Дополнительная характеристика H1 — False Detection

При наличии reference labels допускается расчёт:

- False Positive Rate;
- False Negative Rate;
- Precision;
- Recall.

Например:

\[
Precision =
\frac{TP}{TP+FP}
\]

\[
Recall =
\frac{TP}{TP+FN}
\]

Однако эти показатели применяются только тогда, когда существует достаточно надёжная классификация true/false cases.

---

# 11. Критерий оценки H1

H1 считается:

### Supported

если proposed approach демонстрирует устойчивое улучшение наблюдаемости по сравнению с baseline по заранее выбранному основному показателю и улучшение не сопровождается неприемлемым ростом ложных обнаружений.

### Partially Supported

если улучшение наблюдается только для части сценариев или отдельных классов отклонений.

### Not Supported

если существенного улучшения относительно baseline не выявлено.

### Inconclusive

если данных недостаточно для надёжного сравнения.

Важно:

**не следует заранее фиксировать универсальный процент улучшения как обязательный критерий H1**, пока не известны характеристики данных и baseline.

---

# 12. H2 — Своевременность

## Формулировка H2

**Автоматизированный мониторинг событий и признаков отклонений позволит обнаруживать потенциально проблемные ситуации раньше, чем контроль, основанный преимущественно на ручном просмотре статусов и постфактум анализе.**

---

# 13. Конструкт H2

## Своевременность

Под своевременностью понимается способность обнаружить релевантное событие или проблемную ситуацию с минимальной задержкой относительно момента, когда достаточная информация о ней становится доступной для обнаружения.

Ключевым понятием является:

**Time-to-Detection.**

---

# 14. Определение Time-to-Detection

Для каждого обнаруживаемого события:

\[
TTD = T_{detection} - T_{observable}
\]

где:

- `T_observable` — момент, начиная с которого доступно достаточно evidence для корректного обнаружения;
- `T_detection` — момент, когда исследуемый подход фактически идентифицировал событие.

Важно использовать не просто момент фактического наступления события, а момент **доступности необходимых признаков**, если между ними существует разница.

---

# 15. Почему это важно

Например, проблема может фактически возникнуть в момент:

**10:00**

но необходимая информация появляется только в:

**10:15**.

Если система обнаруживает проблему в:

**10:16**,

то задержка обнаружения составляет:

**1 минута**,

а не 16 минут.

Это предотвращает искусственное завышение преимущества автоматизированного подхода.

---

# 16. Основная метрика H2

## Median Time-to-Detection

Используется медиана TTD по набору сопоставимых случаев.

Медиана предпочтительнее среднего как основной показатель при наличии выбросов.

---

# 17. Дополнительные метрики H2

## 17.1. Mean TTD

Среднее время обнаружения.

Используется дополнительно и интерпретируется вместе с распределением.

## 17.2. P95 TTD

95-й перцентиль времени обнаружения.

Показывает поведение системы в медленных случаях.

## 17.3. Early Detection Rate

\[
EDR =
\frac{N_{proposed\ detects\ before\ baseline}}
{N_{comparable\ cases}}
\]

Показывает долю случаев, в которых proposed approach обнаруживает проблему раньше baseline.

## 17.4. Detection Before Critical Event

Если применимо:

\[
DBCE =
\frac{N_{cases\ detected\ before\ critical\ event}}
{N_{relevant\ cases}}
\]

Показывает, в какой доле случаев информация появляется до критической точки процесса.

---

# 18. Критерий оценки H2

### Supported

если proposed approach систематически снижает TTD относительно baseline и/или увеличивает долю случаев более раннего обнаружения.

### Partially Supported

если улучшение присутствует только в отдельных типах сценариев.

### Not Supported

если существенного улучшения не наблюдается.

### Inconclusive

если данные недостаточны либо момент возникновения observable evidence нельзя определить надёжно.

---

# 19. H3 — Информационная нагрузка

## Формулировка H3

**Агрегированное представление состояния процесса, отклонений и факторов риска позволит сократить объём ручного поиска и сведения информации, необходимой для принятия управленческого решения.**

---

# 20. Конструкт H3

Под информационной нагрузкой в рамках исследования понимается совокупность действий и времени, необходимых пользователю для поиска, сопоставления и преобразования информации, требуемой для выполнения заданной аналитической или управленческой задачи.

Информационная нагрузка не сводится только ко времени.

---

# 21. Основная метрика H3

## Task Completion Time

\[
TCT = T_{finish} - T_{start}
\]

где:

- `T_start` — момент начала выполнения задачи;
- `T_finish` — момент получения достаточного результата.

Основным сравнением является:

\[
\Delta TCT =
TCT_{baseline} - TCT_{proposed}
\]

и относительное изменение:

\[
Improvement =
\frac{TCT_{baseline}-TCT_{proposed}}
{TCT_{baseline}}
\]

---

# 22. Дополнительные метрики H3

## 22.1. Number of Actions

Количество действий пользователя:

- открытия;
- поиска;
- переходы;
- ручные фильтрации;
- копирование;
- сопоставление;
- ручной расчёт.

---

## 22.2. Number of Information Sources

Количество отдельных источников, которые необходимо использовать для решения задачи.

Например:

- система;
- Excel-файл;
- журнал;
- PDF;
- другая система.

---

## 22.3. Number of Context Switches

Количество переключений между информационными источниками.

Это особенно важно, если задача требует постоянного перехода между системами.

---

## 22.4. Manual Transformation Count

Количество ручных информационных преобразований:

- копирование;
- объединение;
- сортировка;
- фильтрация;
- ручное сопоставление;
- повторный ввод.

---

## 22.5. Task Accuracy / Completeness

Ускорение не считается улучшением, если пользователь получает неправильный или неполный результат.

Поэтому результаты должны проверяться на:

- correctness;
- completeness.

---

# 23. Условия сравнения H3

Baseline и proposed должны решать:

**одинаковую или функционально эквивалентную задачу.**

Пример:

**Задача:** определить текущие проблемные экземпляры процесса и причину задержки.

Baseline:

пользователь ищет данные в нескольких источниках.

Proposed:

пользователь работает с агрегированным представлением.

При этом критерии правильного ответа одинаковы.

---

# 24. Критерий оценки H3

### Supported

если proposed approach уменьшает Task Completion Time и/или объём ручных операций при сохранении приемлемой корректности результата.

### Partially Supported

если снижается только часть компонентов нагрузки.

Например:

- время сокращается;
- но число действий остаётся почти тем же.

### Not Supported

если измеримого снижения нагрузки не наблюдается.

### Inconclusive

если задача недостаточно стандартизирована или выборка слишком мала для сопоставления.

# 26. Measurement Levels

Для показателей используется несколько уровней анализа.

## Event Level

Отдельное событие.

Используется для:

- timestamp;
- event type;
- state transition.

## Case Level

Отдельный экземпляр процесса.

Используется для:

- cycle time;
- number of deviations;
- TTD.

## Scenario Level

Определённый контролируемый сценарий.

Используется для:

- baseline/proposed comparison;
- task evaluation.

## Aggregate Level

Совокупность случаев.

Используется для:

- median;
- mean;
- percentile;
- rates.

---

# 27. Baseline Specification

Baseline должен быть зафиксирован до проведения финального сравнения.

Документируются:

- источник информации;
- доступные данные;
- последовательность действий;
- способ обнаружения отклонений;
- ручные операции;
- время выполнения;
- используемые источники;
- критерии завершения задачи.

Baseline должен отражать **реальный или реалистично реконструированный существующий процесс**, а не намеренно ухудшенный вариант.

---

# 28. Proposed Approach Specification

Proposed approach должен использовать ту функциональность, которую исследование действительно предлагает оценить.

Фиксируются:

- входные данные;
- preprocessing;
- event representation;
- state representation;
- analytical processing;
- deviation detection;
- output;
- user interaction;
- logging of detection time;
- измеряемые результаты.

Нельзя добавлять функции только ради улучшения экспериментального результата, если они отсутствуют в концептуальной модели решения.

---

Это предотвращает смешивание разных уровней анализа.

# 31. Statistical Evaluation

Статистические методы выбираются после определения реального объёма и свойств данных.

При достаточной выборке допускается использование:

- descriptive statistics;
- confidence intervals;
- paired comparison;
- effect size;
- appropriate significance testing.

При малом объёме данных основной акцент может быть сделан на:

- case-level comparison;
- distribution analysis;
- median differences;
- scenario-level results;
- effect direction;
- qualitative interpretation.

Нельзя создавать видимость статистической строгости при недостаточной выборке.

---

# 32. Effect Size

Помимо вопроса:

**«есть ли разница?»**

желательно оценивать:

**«насколько велика разница?»**

Для ключевых показателей рекомендуется фиксировать:

\[
\Delta = Metric_{proposed} - Metric_{baseline}
\]

и относительное изменение:

\[
Relative\ Change =
\frac{Metric_{proposed}-Metric_{baseline}}
{Metric_{baseline}}
\]

Знак интерпретируется в зависимости от показателя.

Для показателей, где меньше — лучше:

- TTD;
- Task Completion Time;
- Actions;

отрицательное изменение может означать улучшение.

Для показателей, где больше — лучше:

- Detection Completeness;
- Coverage;

положительное изменение означает улучшение.

# 34. Guard Metrics

Основной показатель не должен оцениваться изолированно.

Для контроля качества используются guard metrics.

Например:

**H1**

повышение Detection Completeness не должно достигаться только за счёт резкого роста false positives.

**H2**

снижение TTD не должно достигаться за счёт ранних, но недостоверных предупреждений.

**H3**

снижение времени не должно сопровождаться снижением Accuracy или Completeness.

Таким образом:

**эффективность + качество**

оцениваются одновременно.

---

# 35. Decision Rules

Для каждой гипотезы используется четырёхуровневая шкала.

## Supported

Основной эффект наблюдается и проходит установленные проверки качества.

## Partially Supported

Эффект существует, но зависит от сценария, типа отклонения или другого условия.

## Not Supported

Ожидаемого эффекта не обнаружено.

## Inconclusive

Полученных данных недостаточно для вывода.

Это предпочтительнее бинарного:

**accepted / rejected**

поскольку исследование имеет прикладной и кейс-ориентированный характер.

---

# 36. Threats to Measurement Validity

## Measurement Bias

Возникает, если способ измерения отличается между baseline и proposed.

### Контроль

Одинаковые definitions и одинаковая процедура расчёта.

---

## Detection Bias

Момент обнаружения определяется по-разному.

### Контроль

Заранее определить:

**T_observable**

и

**T_detection**.

---

## Learning Effect

Пользователь после выполнения baseline может выполнить proposed быстрее просто потому, что уже знает задачу.

### Контроль

По возможности:

- рандомизация порядка;
- разные, но эквивалентные сценарии;
- несколько повторений.

---

## Scenario Bias

Отдельный сценарий может случайно благоприятствовать предлагаемому подходу.

### Контроль

Использовать несколько типов сценариев.

---

## Data Leakage

Если proposed approach получает данные, которые недоступны baseline, сравнение становится нечестным.

### Контроль

Чётко документировать доступность данных для обеих сторон.

---

### H2

**Early Detection Rate**.

**Task Completion Time**

+

**Actions**

+

**Sources**

+

**Manual Transformations**

+

**Accuracy/Completeness**.

# 40. Minimum Evaluation Package

Для минимально достаточной проверки исследования должны существовать:

### H1

- reference deviation set;
- baseline result;
- proposed result;
- Detection Completeness;
- analysis of incorrect detections, если применимо.

### H2

- определение T_observable;
- baseline detection time;
- proposed detection time;
- Median TTD;
- distribution / percentile analysis.

### H3

- стандартизированная задача;
- baseline execution;
- proposed execution;
- Task Completion Time;
- actions / sources / manual transformations;
- correctness/completeness.

# 41. Data Sufficiency Check

До начала финального эксперимента необходимо проверить:

### H1

Есть ли достаточно надёжный reference set?

### H2

Можно ли однозначно определить момент доступности evidence?

### H3

Можно ли стандартизировать задачу и сравнить выполнение?

Если ответ отрицательный, необходимо сначала изменить Measurement Procedure, а не искусственно рассчитывать показатель.

# 44. Ограничения оценки

Результаты evaluation должны интерпретироваться с учётом:

- конкретного исследуемого процесса;
- выбранного кейса;
- доступности данных;
- размера выборки;
- качества event records;
- степени реалистичности синтетических данных;
- вариативности пользовательских действий;
- ограничений экспериментального сценария.

Полученный эффект не должен автоматически распространяться на все процессы ТОиР.

# 45. Критерий завершения Framework

`Measurement & Evaluation Framework v1` считается завершённым, если:

1. H1–H3 операционализированы;
2. для каждого конструкта определены переменные;
3. определены основные и дополнительные метрики;
4. описаны формулы;
5. определён baseline;
6. определён proposed approach;
7. установлены единицы анализа;
8. заданы критерии корректности;
9. предусмотрены guard metrics;
10. определены правила интерпретации;
11. описаны потенциальные threats to validity;
12. есть минимальный набор данных для проверки каждой гипотезы.

# 46. Итог

В рамках исследования зафиксирована следующая система оценки:

**H1 — Наблюдаемость**

Основной показатель:

**Detection Completeness**

Дополнительные:

**Event Coverage, State Coverage, Deviation Coverage.**

---

**H2 — Своевременность**

Основной показатель:

**Median Time-to-Detection**

Дополнительные:

**P95 TTD, Early Detection Rate, Detection Before Critical Event.**

---

**H3 — Информационная нагрузка**

Основной показатель:

**Task Completion Time**

Дополнительные:

**Number of Actions, Number of Sources, Context Switches, Manual Transformations, Accuracy, Completeness.**

---

Центральное правило оценки:

> **Предлагаемый подход считается улучшением не тогда, когда он просто производит больше информации или работает быстрее, а когда он обеспечивает измеримое улучшение соответствующего конструкта при сохранении приемлемой корректности результата.**

Таким образом, `Measurement & Evaluation Framework v1` превращает H1–H3 из концептуальных гипотез в **проверяемую систему измерения**, которую можно использовать при разработке экспериментального протокола и последующей оценке предлагаемого решения.
