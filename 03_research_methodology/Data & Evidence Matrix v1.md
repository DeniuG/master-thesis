# Data & Evidence Matrix v1

## 1. Назначение документа

`Data & Evidence Matrix v1` определяет, какие данные и другие виды исследовательских доказательств необходимы для получения обоснованных ответов на `RQ0–RQ13`, откуда они могут быть получены, в каком виде представлены, для каких аналитических операций используются и какие выводы допустимо на их основании делать.

Документ является связующим звеном между:

**Research Questions**

→ **Methods**

→ **Data / Evidence**

→ **Analysis**

→ **Results**

→ **Evaluation**.

Основная цель матрицы — предотвратить ситуацию, при которой исследовательский вопрос или гипотеза формулируются без заранее понятной доказательной базы.

---

# 2. Принцип evidence-driven research

В рамках исследования применяется правило:

> **Нельзя считать исследовательский вывод обоснованным до тех пор, пока не определено, какое evidence его поддерживает и каким образом это evidence анализируется.**

Поэтому для каждого существенного вывода должны быть известны:

**Что наблюдаем?**

→ **где получаем?**

→ **в каком формате?**

→ **как анализируем?**

→ **что можем утверждать?**

→ **какие существуют ограничения?**

---

# 3. Типы исследовательских данных и evidence

Все evidence делятся на несколько категорий.

## 3.1. Process Evidence

Данные о фактическом прохождении процесса:

- операции;
- этапы;
- действия;
- переходы;
- события;
- статусы;
- временные отметки;
- возвраты;
- отклонения;
- завершения.

## 3.2. Information Evidence

Данные о том, где и как хранится и используется информация:

- информационные системы;
- таблицы;
- файлы;
- документы;
- журналы;
- интерфейсы;
- отчёты;
- ручные записи;
- информационные преобразования.

## 3.3. Organizational Evidence

Информация о:

- ролях;
- ответственности;
- участниках;
- точках передачи;
- правилах принятия решений;
- эскалациях.

## 3.4. Documentary Evidence

- нормативные документы;
- регламенты;
- инструкции;
- процедуры;
- формы;
- описания процессов;
- техническая документация.

## 3.5. Expert Evidence

- интервью;
- экспертные оценки;
- структурированные ответы;
- верификация моделей;
- экспертное ранжирование.

## 3.6. Scientific Evidence

- научные публикации;
- существующие модели;
- методологические подходы;
- результаты предыдущих исследований.

## 3.7. Experimental Evidence

- baseline;
- proposed approach;
- тестовые сценарии;
- синтетические данные;
- результаты эксперимента;
- временные и количественные показатели.

# 4. Уровни доказательности

Evidence классифицируется по степени непосредственной связи с фактическим явлением.

### Level A — Direct Evidence

Непосредственные записи или наблюдения:

- event logs;
- timestamps;
- системные записи;
- фактические документы;
- прямое наблюдение.

### Level B — Structured Evidence

Структурированные результаты:

- BPMN;
- process maps;
- KPI tables;
- data matrices;
- классифицированные отклонения.

### Level C — Expert Evidence

Интервью и экспертные оценки.

### Level D — Documentary / Secondary Evidence

Документы, описания, публикации и другие вторичные источники.

### Level E — Working Assumption

Предположение или рабочая гипотеза, подлежащая последующей проверке.

Ключевые эмпирические выводы по возможности должны опираться на Level A и B.

# 6. Детальная структура данных для процессного анализа

Для последующего анализа событий рекомендуется использовать минимальную логическую структуру event record.

| Поле | Назначение | Обязательность |
|---|---|---|
| `Case ID` | идентификация экземпляра процесса | желательно обязательное |
| `Event ID` | идентификация события | желательно |
| `Activity` | действие/операция | обязательно |
| `Timestamp` | время события | обязательно для temporal analysis |
| `Status` | состояние/статус | желательно |
| `Resource / Role` | исполнитель или роль | желательно |
| `Object ID` | связанный объект ТОиР | по необходимости |
| `Source` | источник записи | рекомендуется |
| `Event Type` | тип события | рекомендуется |
| `Attributes` | дополнительные характеристики | по необходимости |

При отсутствии конкретного поля это должно быть явно зафиксировано как ограничение данных.

# 7. Сущности, которые должны быть разделены

При работе с данными не следует автоматически считать одинаковыми:

**Process Instance**

и

**Event**

и

**State**

и

**Status**

и

**Document**

и

**Management Decision**.

Например:

**статус «в работе»**

не обязательно является отдельным процессным событием.

А изменение статуса:

**«в работе» → «завершено»**

может являться событием, фиксирующим переход состояния.

Эта разница критична для последующей реконструкции процесса.

# 8. Data Requirements по RQ

## RQ1 — Domain Understanding

### Необходимые данные

- перечень процессов;
- названия операций;
- роли;
- входы;
- выходы;
- используемые документы;
- основные правила;
- взаимодействия между участниками.

### Источники

- нормативная документация;
- инструкции;
- интервью;
- наблюдение.

### Основной риск

Документ может отражать **нормативный процесс**, но не фактическую практику.

Поэтому documentary evidence должно проверяться через наблюдение или экспертное подтверждение.

---

# 9. RQ2 — AS-IS Reconstruction

### Необходимые данные

Минимальный набор:

**операция + последовательность + исполнитель + условия перехода.**

Желательно также:

**timestamp + status + exception + rework.**

### Источники

- наблюдение;
- рабочие документы;
- системные записи;
- интервью.

### Особая необходимость

Необходимо фиксировать не только «нормальный путь», но и:

- альтернативные ветки;
- возвраты;
- повторные действия;
- ожидания;
- исключения;
- ручные обходные процедуры.

---

# 10. RQ3 — Event / State Evidence

Для RQ3 особенно важно определить **наблюдаемость**.

Наличие записи в информационной системе ещё не означает, что она позволяет восстановить реальное выполнение процесса.

Для каждого события желательно проверить:

**Можно ли определить:**

1. что произошло;
2. когда произошло;
3. к какому экземпляру процесса относится;
4. какой объект затронут;
5. кто/какая роль инициировала действие;
6. какое состояние было до события;
7. какое состояние возникло после события.

Если часть этих характеристик недоступна, это само по себе является evidence информационного GAP.

---

# 11. RQ4 — Problem Evidence

Каждая выявленная проблема получает собственный идентификатор.

Рекомендуемая структура:

| Поле | Содержание |
|---|---|
| Problem ID | уникальный идентификатор |
| Process Step | участок процесса |
| Problem Description | описание |
| Observable Symptom | наблюдаемый признак |
| Evidence Source | источник |
| Evidence Type | тип evidence |
| Frequency | частота, если доступна |
| Impact | последствие |
| Candidate Cause | возможная причина |
| KPI | измеримый признак |
| Confidence | уровень уверенности |

Это позволяет не смешивать фактическое наблюдение и интерпретацию.

---

# 12. RQ5 — Evidence for Root Causes

Для каждой причины необходимо разделить:

### Observed

Что непосредственно наблюдается.

### Inferred

Что логически выводится из observations.

### Expert-Assessed

Что подтверждается экспертами.

### To Be Verified

Что пока является рабочей гипотезой.

Например:

**Observed:** операция повторяется.

**Inferred:** существует недостаток информации или ошибка на предыдущем этапе.

**Expert-Assessed:** причиной считается неполная передача данных.

**To Be Verified:** конкретный информационный источник, вызывающий проблему.

Такое разделение защищает исследование от преждевременных причинно-следственных выводов.

---

# 13. RQ6 — Measurement Data

Для каждого KPI требуется определить полный data lineage:

**Raw Data**

→ **Transformation**

→ **Metric**

→ **Interpretation**.

Например:

`Event timestamps`

→

`duration = completion_time - start_time`

→

`Cycle Time`

→

`comparison between baseline and proposed approach`.

Для временных KPI необходимо отдельно определять:

- начало измерения;
- конец измерения;
- timezone;
- единицу времени;
- правила обработки отсутствующих timestamps;
- правила обработки дубликатов.

---

# 14. RQ7 — Information Landscape Evidence

Для каждого информационного источника следует фиксировать:

| Поле | Содержание |
|---|---|
| Source ID | идентификатор |
| Source Type | система / файл / документ / журнал |
| Information Content | какая информация содержится |
| Process Step | где используется |
| User / Role | кто использует |
| Update Frequency | частота обновления |
| Accessibility | доступность |
| Structuredness | структурированность |
| Manual Handling | ручная обработка |
| Integration | наличие интеграции |
| Analytical Use | аналитическое использование |
| Limitation | ограничение |

Это позволит в дальнейшем объективнее построить GAP Matrix.

---

# 15. RQ8 — Scientific and Comparative Evidence

Для каждого метода или класса решения необходимо хранить:

- источник;
- тип публикации/решения;
- задача;
- требуемые данные;
- необходимые условия применения;
- сильные стороны;
- ограничения;
- требования к инфраструктуре;
- степень интерпретируемости;
- применимость к исследуемому процессу.

Особенно важно разделить:

**method is theoretically applicable**

и

**method is practically feasible in the investigated case.**

---

# 16. RQ9 — GAP Evidence

Каждый GAP должен иметь минимум четыре элемента:

**Need**

→

**Required Capability**

→

**Existing Capability**

→

**Observed Limitation**.

Только после этого формируется:

**GAP**

### Пример логики

Требуется раннее обнаружение отклонений.

↓

Существующая система предоставляет только текущий статус.

↓

История событий и автоматическое сравнение отсутствуют.

↓

Возникает функциональный GAP в области event-based monitoring.

Это не означает автоматически, что решение должно использовать конкретный алгоритм.

---

# 17. RQ10 — Requirement Evidence

Каждое требование должно иметь происхождение.

Рекомендуемая структура:

**Requirement ID**

→

**Source Problem**

→

**GAP**

→

**Requirement**

→

**Purpose**

→

**Acceptance Criterion**.

Это позволит создать полноценную Requirements Traceability Matrix.

---

# 18. RQ11 — Evidence for Conceptual Design

Концептуальная модель должна опираться не на абстрактное «так будет лучше», а на:

- выявленные события;
- состояния;
- информационные ограничения;
- требования;
- результаты RQ8;
- KPI;
- ограничения доступных данных.

Для каждого компонента предлагаемого решения необходимо понимать:

**какой GAP он закрывает.**

---

# 19. Experimental Evidence для RQ12

Для проверки H1 и H2 необходимы сопоставимые данные.

Минимальная структура:

| Поле | Описание |
|---|---|
| Scenario ID | идентификатор сценария |
| Case ID | экземпляр процесса |
| True Event | фактически возникшее событие |
| Detection Baseline | обнаружение baseline |
| Detection Proposed | обнаружение proposed |
| Time Baseline | время обнаружения baseline |
| Time Proposed | время обнаружения proposed |
| Correct Detection | корректность |
| False Positive | ложное срабатывание, если измеримо |
| False Negative | пропущенное событие, если измеримо |

### Для H1

Нас интересует:

**что удалось увидеть.**

### Для H2

Нас интересует:

**когда это удалось увидеть.**

Поэтому эти два конструкта должны анализироваться отдельно.

# 20. Experimental Evidence для RQ13

Для H3 единицей анализа может быть **task execution**.

Для каждой попытки фиксируется:

- Task ID;
- Scenario ID;
- Baseline / Proposed;
- start time;
- completion time;
- elapsed time;
- number of actions;
- number of opened sources;
- number of context switches;
- number of manual transformations;
- correctness/completeness;
- user assessment, если используется.

Это позволяет отделить:

**быстрее найти информацию**

от

**меньше физически обработать информации**

и от

**лучше выполнить управленческую задачу**.

# 22. Работа с отсутствующими данными

Отсутствие данных не должно скрываться.

Каждый недостаток должен классифицироваться.

### Missing

Данные существуют концептуально, но физически недоступны.

### Unstructured

Данные существуют, но не имеют пригодной структуры.

### Incomplete

Есть только часть необходимых записей.

### Inconsistent

Источники противоречат друг другу.

### Unobservable

Необходимое состояние процесса вообще не фиксируется.

### Restricted

Доступ ограничен организационными или правовыми условиями.

Эти состояния сами могут стать частью анализа информационного GAP.

---

# 23. Стратегия при отсутствии полноценного Event Log

Если отсутствует полноценный event log, исследование не прекращается.

Используется комбинированный evidence:

**Documents**

+

**Observation**

+

**Interviews**

+

**Available System Records**

→

**Partial Event Model**

→

**Observed Process Model**

→

**Gap Identification**.

При этом необходимо честно обозначать границы:

> невозможность полной реконструкции процесса по event log является ограничением эмпирической части, а не основанием для искусственного формирования отсутствующих событий.

---

# 24. Синтетические данные

Синтетические данные допускаются для:

- проверки алгоритма;
- проверки логики обнаружения;
- контролируемых сценариев;
- анализа edge cases;
- воспроизводимого технического эксперимента.

Однако необходимо сохранять разделение:

**Empirical Evidence**

и

**Synthetic Experimental Evidence**.

Результат, полученный исключительно на синтетических данных, не должен формулироваться как доказательство того, что аналогичный эффект уже наблюдается в реальной организации.

---

# 25. Metadata и Data Provenance

Для каждого набора данных рекомендуется фиксировать:

- название источника;
- дата получения;
- период покрытия;
- тип источника;
- версия;
- владелец/ответственный, если допустимо;
- формат;
- объём;
- ограничения;
- правила очистки;
- произведённые преобразования.

Для экспериментальных данных дополнительно:

- версия алгоритма/метода;
- параметры;
- сценарий;
- дата запуска;
- seed, если используется случайность;
- критерии оценки.

# 26. Data Quality Framework

Перед использованием данных следует проверять:

### Completeness

Насколько полно представлены необходимые события или записи.

### Accuracy

Соответствуют ли записи фактическому состоянию.

### Consistency

Не противоречат ли различные источники друг другу.

### Timeliness

Насколько актуальны данные.

### Granularity

Достаточна ли детализация.

### Traceability

Можно ли связать запись с конкретным процессом/объектом.

### Availability

Доступны ли данные для воспроизводимого исследования.

### Interpretability

Можно ли однозначно понять значение полей и событий.

# 27. Минимальные требования к данным для проверки H1–H3

## Для H1

Необходимы:

- определённый набор релевантных отклонений;
- возможность установить факт их возникновения;
- возможность определить, обнаружены они или нет.

## Для H2

Дополнительно необходимы:

- timestamp возникновения/доступности признака;
- timestamp обнаружения;
- единые правила определения начала и конца интервала.

## Для H3

Необходимы:

- одинаковая управленческая задача;
- сопоставимые условия;
- фиксируемая последовательность действий;
- время выполнения;
- количество действий/источников или иной заранее заданный показатель нагрузки.

|---|---|

# 29. Evidence Integrity Rules

В рамках исследования фиксируются следующие правила.

### Rule 1

Не называть предположение фактом.

### Rule 2

Не использовать экспертное мнение как замену количественным данным, если количественные данные доступны.

### Rule 3

Не использовать один источник для критически важного вывода без проверки альтернативных объяснений, если triangulation возможна.

### Rule 4

Не скрывать отсутствующие или неполные данные.

### Rule 5

Не смешивать реальные и синтетические данные без явной маркировки.

### Rule 6

Не выводить причинность только из корреляции.

### Rule 7

Не считать наличие записи доказательством фактического выполнения операции без проверки семантики записи.

### Rule 8

Каждый KPI должен иметь определённый источник raw data.

### Rule 9

Каждое требование должно иметь traceability к проблеме или GAP.

### Rule 10

Каждый критерий экспериментальной оценки должен соответствовать соответствующей гипотезе.

# 30. Критерий завершения Data & Evidence Matrix

Документ считается подготовленным, если:

1. `RQ0–RQ13` имеют определённую evidence base;
2. для каждого RQ определены возможные источники;
3. различены direct, structured, expert и documentary evidence;
4. определены минимальные требования к данным;
5. описаны потенциальные проблемы качества данных;
6. установлены правила работы с отсутствующими данными;
7. определены минимальные данные для H1–H3;
8. существует traceability от evidence к итоговому выводу;
9. реальные и синтетические данные разделены;
10. evidence framework не предполагает заранее положительного результата.
